Gobierno de Datos & Convenciones de Nomenclatura

Un Data Warehouse robusto requiere un estándar riguroso. Se implementaron reglas estrictas de Naming Conventions utilizando snake_case para asegurar la coherencia en todos los esquemas lógicos y facilitar la trazabilidad del linaje de datos entre las fuentes de origen (CRM/ERP) y las tablas analíticas.

  • Estandarización de Tablas Crudas (Bronce & Plata)Las entidades mantienen el nombre de su sistema de origen para asegurar trazabilidad. Patrón: <sourcesystem>_<entity> (Ej. crm_customer_info).
  • Modelado de Negocio (Oro)Las tablas finales utilizan nombres descriptivos alineados al dominio de negocio, utilizando los prefijos dim_ para Dimensiones y fact_ para Hechos.
  • Metadatos Técnicos & AuditoríaToda columna autogenerada por el sistema para propósitos de auditoría inicia con el prefijo dwh_ (Ej. dwh_create_date). Toda llave subrogada utiliza el sufijo _key.

Diseño de Arquitectura y Metodología ETL

Integrando conceptos de Kimball y Data Lakehouses, se diseñó una Arquitectura Medallón lógica en SQL Server. Esta aproximación garantiza la separación de responsabilidades (SoC) entre la ingesta cruda, la transformación y el consumo de datos.

Capa de Datos Objetivo y Tipo de Objeto Transformaciones Aplicadas Método de Carga
Capa Bronce Trazabilidad. Tablas físicas (Raw Tables). Datos almacenados "As-Is". Ninguna (As-Is). Carga Completa (Truncate & Insert).
Capa Plata Limpieza y preparación. Tablas físicas (Cleaned Tables). Data Cleansing, Normalización, Estandarización y Columnas Derivadas. Carga Completa (Truncate & Insert).
Capa Oro Consumo por negocio (BI & Analytics). Vistas Analíticas. Data Integration, Agregaciones, Lógica de Negocio y Data Modeling (Star Schema). Ninguna (Son Vistas en tiempo real).

Fase 1: Capa Bronce (Data Ingestion)

Se desarrolló un motor de ingesta (Stored Procedure: bronze.load_bronze) enfocado en el rendimiento masivo. Implementa un método BULK INSERT bajo el estándar de carga completa (Full Load). Se aplicó un patrón Idempotente de reinicio seguro (TRUNCATE antes de insertar) y un bloque de auditoría TRY...CATCH para trazabilidad de errores.

proc_load_bronze.sql (Extracto Idempotente) 
CREATE OR ALTER PROCEDURE bronze.load_bronze AS
BEGIN
    BEGIN TRY
        SET @start_time = GETDATE();
        TRUNCATE TABLE bronze.crm_sales_details;
        
        BULK INSERT bronze.crm_sales_details
        FROM 'C:\SQL_Datasets\source_crm\sales_details.csv'
        WITH (
            FIRSTROW = 2,
            FIELDTERMINATOR = ',',
            TABLOCK -- Optimización de rendimiento de escritura (Bloqueo a nivel tabla)
        );
        
        SET @end_time = GETDATE();
        PRINT '>> Load Duration: ' + CAST(DATEDIFF(second, @start_time, @end_time) AS NVARCHAR) + ' sec';
    END TRY
    BEGIN CATCH
        PRINT 'ERROR OCCURRED: ' + ERROR_MESSAGE();
    END CATCH
END

Fase 2: Capa Plata (Limpieza & QA)

En esta capa se ejecuta la transformación de negocio de los datos (Data Cleansing). Todo el proceso está automatizado mediante un Stored Procedure maestro (silver.load_silver) que ejecuta de manera transaccional el truncado, la transformación y la inserción de todas las tablas.

El objetivo es preparar los datos para análisis, realizando validaciones matemáticas rigurosas, estandarización de columnas y normalización de fechas históricas aplicando Funciones de Ventana (Window Functions) para generar intervalos sin solapamiento.

proc_load_silver.sql (Transformación y Automatización) 
CREATE OR ALTER PROCEDURE silver.load_silver AS
BEGIN
    BEGIN TRY
        PRINT '>> Truncating Table: silver.crm_prd_info';
        TRUNCATE TABLE silver.crm_prd_info;
        
        PRINT '>> Inserting Data Into: silver.crm_prd_info';
        INSERT INTO silver.crm_prd_info (prd_id, cat_id, prd_key, prd_cost, prd_end_dt)
        SELECT
            prd_id,
            -- 1. Extracción de Llaves Foráneas ocultas en cadenas de texto
            REPLACE(SUBSTRING(prd_key, 1, 5), '-', '_') AS cat_id,
            SUBSTRING(prd_key, 7, LEN(prd_key)) AS prd_key,
            
            -- 2. Manejo de valores faltantes y nulos
            ISNULL(prd_cost, 0) AS prd_cost,
            
            -- 3. Window Function (LEAD) para dimensionamiento de cambio lento (SCD2)
            CAST(
                LEAD(prd_start_dt) OVER (PARTITION BY prd_key ORDER BY prd_start_dt) - 1 
                AS DATE
            ) AS prd_end_dt
        FROM bronze.crm_prd_info;
        
        PRINT '>> Proceso Capa Plata Completado Exitosamente.';
    END TRY
    BEGIN CATCH
        PRINT 'ERROR OCCURRED IN SILVER LAYER: ' + ERROR_MESSAGE();
    END CATCH
END

Suite de Pruebas (Data Quality Assurance)

Una vez finalizada la inserción del Stored Procedure, se ejecutan scripts de validación (QA) para garantizar la exactitud de los datos limpios antes de pasar al modelado dimensional.

quality_checks_silver.sql (Data Profiling & QA) 
-- 1. Verificación de Integridad: Detección de Nulos o Duplicados en Llaves Primarias
SELECT 
    prd_id,
    COUNT(*) 
FROM silver.crm_prd_info
GROUP BY prd_id
HAVING COUNT(*) > 1 OR prd_id IS NULL;

-- 2. Consistencia Matemática: Auditoría de Ventas = Cantidad * Precio
SELECT DISTINCT 
    sls_sales,
    sls_quantity,
    sls_price 
FROM silver.crm_sales_details
WHERE sls_sales != sls_quantity * sls_price
   OR sls_sales IS NULL 
   OR sls_quantity IS NULL 
   OR sls_price IS NULL
   OR sls_sales <= 0;

Fase 3: Capa Oro (Modelado Dimensional)

La capa analítica final (Sales Data Mart) se construyó mediante Vistas Analíticas. Se implementó un Modelo de Estrella puro generando Llaves Subrogadas (Surrogate Keys) dinámicas para independizar el Data Warehouse de los cambios en los sistemas origen. Las métricas de ventas centralizadas conectan con las dimensiones normalizadas mediante relaciones de Uno-a-Muchos.

Modelo Dimensional en Estrella (Data Mart)

Diseño Entidad-Relación final implementado en la Capa Oro: fact_sales unida mediante Foreign Keys a las dimensiones dim_customers y dim_products.

ddl_gold.sql (Generación de Llaves Subrogadas) 
CREATE VIEW gold.dim_customers AS
SELECT
    -- Generación de Llave Subrogada dinámica para aislamiento del modelo analítico
    ROW_NUMBER() OVER (ORDER BY cst_id) AS customer_key, 
    
    ci.cst_firstname AS first_name,
    la.cntry         AS country,
    
    -- Data Integration (Resolución de Conflictos entre fuentes CRM vs ERP)
    CASE 
        WHEN ci.cst_gndr != 'n/a' THEN ci.cst_gndr -- Regla de Negocio: CRM es el maestro
        ELSE COALESCE(ca.gen, 'n/a')               -- Fallback: ERP como fuente de respaldo
    END AS gender
FROM silver.crm_cust_info ci
LEFT JOIN silver.erp_cust_az12 ca ON ci.cst_key = ca.cid;

Fase 4: Análisis Exploratorio (EDA)

Tras modelar el Data Warehouse, ejecutamos un proceso de Análisis Exploratorio (EDA) para interrogar la Capa Oro utilizando T-SQL. A través de agregaciones y segmentaciones cruzadas entre Dimensiones y Medidas, se descubrieron tendencias críticas para el negocio y Insights procesables.

eda_analysis.sql (Ranking con Window Functions) 
-- Reporte: Identificar los 5 productos más rentables del histórico
SELECT * FROM (
    SELECT 
        p.product_name,
        SUM(f.sales_amount) AS total_revenue,
        RANK() OVER (ORDER BY SUM(f.sales_amount) DESC) AS sales_rank
    FROM gold.fact_sales f
    LEFT JOIN gold.dim_products p 
        ON f.product_key = p.product_key
    GROUP BY p.product_name
) ranking_query
WHERE sales_rank <= 5;
